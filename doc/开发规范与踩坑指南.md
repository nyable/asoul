## 1. 核心架构与设计规范

### 1.1 三层模型隔离铁律

系统的核心数据流向**必须严格遵循三层模型**，绝对禁止跨层直达：

```text
Source (Git / Local / Managed)
   │
   ▼ [add / update]
Managed Store (<workspace>/skills/)
   │
   ▼ [deploy / undeploy]
Target (~/.codex/skills, etc.)
```

- **严禁**：从 Git Source 直接安装到 Agent Target。
- **原因**：Agent Target 只是受管副本的分发出口；所有的版本追踪、冲突检测、修改保护和 Diff 对比均依赖 `Managed Store` 中的实体与 `catalog.json` 元数据。

### 1.2 CLI 与 TUI 核心逻辑共享

- `internal/app/service.go` 是所有业务逻辑的唯一执行层。
- CLI 命令（`internal/cli/`）和 TUI 界面（`internal/tui/`）只负责参数解析、界面渲染与交互，**禁止**在 CLI 或 TUI 中实现任何私有的工作区读写、Git 拉取或部署逻辑。

### 1.3 目标系统与项目工程显式管理铁律（Explicit Management, No Implicit Magic）

- **严禁隐式注入当前工作目录**：
  - 无论在 TUI 的 Target 列表加载（`reloadTargets`）还是部署弹窗候选生成（`newDeployModal`）中，**绝对禁止**调用 `os.Getwd()` 隐式将 `.` 或当前目录塞入用户工程列表。
  - 项目工程列表必须完全忠于用户的显式操作（通过 `config.jsonc` 声明、`asoul project add <path>` 命令登记，或在 TUI 中主动按 `a` 键添加）。
- **用户对所有条目拥有平等的掌控权**：
  - 不得对任何条目设置“不可删除”或特殊豁免（例如以往对当前工作目录的拦截 `Cannot remove current directory from list`，该类特化逻辑已被彻底废弃）。
  - 所有项目和渠道均支持启用/禁用（`enabled`）以及移除操作（`x` / `del`）。

## 2. 终端 UI (TUI) 开发规范与踩坑总结

TUI 基于 [Bubble Tea](https://github.com/charmbracelet/bubbletea) 与 [Lipgloss](https://github.com/charmbracelet/lipgloss) 构建。在终端环境下排版与表格渲染具有特殊的复杂性，以下是核心规范与常见陷阱：

### 2.1 踩坑点 1：中文字符全角宽度与 UTF-8 字节长度的错位陷阱

#### 问题表现
在“技能管理”等表格中，表头 `"技能名称"` 与数据行的英文技能名完全无法对齐，第二列及后续列出现 4 列以上的向左/向右整体错乱偏移。

#### 原因剖析
- Go 标准库的 `fmt.Sprintf("%-20s", text)` 与 `len(text)` 是基于 **字节数（Byte Count）** 计算宽度的。
- 在 UTF-8 中，一个汉字占 **3 个字节**；但在标准终端显示屏上，一个汉字占 **2 个显示单元格列宽（East Asian Full-Width）**。
- 例：`"技能名称"` 包含 4 个汉字 = 12 字节。使用 `%-20s` 时，Go 只补了 `20 - 12 = 8` 个半角空格。在终端视觉呈现为：4 个汉字（8 列宽） + 8 个空格（8 列宽） = **16 列宽**。
- 而数据行的英文技能名（如 `my-demo-skill`，13 字节/13 列宽）使用 `%-20s` 会补 7 个空格，视觉宽度为 **20 列宽**。
- **结果**：表头列宽比数据列宽整整少了 4 列，导致后续所有列在视觉上彻底错乱！

#### 规范与最佳实践
- **禁止使用 `fmt.Sprintf("%-Ns", ...)` 对表格列进行对齐排版**。
- **必须使用基于终端列宽的计算函数**：本项目统一封装了 `padCell(s string, width int) string`（位于 `internal/tui/table.go`）。
- `padCell` 内部依赖 `lipgloss.Width(s)`，能够精准识别中文字符全角列宽并正确补齐空格，确保终端屏幕上的视觉列宽严格等于 `width`。

---

### 2.2 踩坑点 2：ANSI 颜色转义代码对列宽计算的破坏

#### 问题表现
状态徽章（如绿色的 `clean`、黄色的 `modified`）添加颜色样式后，状态列及后续所有列（上游状态、详情/Hash）全部向左崩塌错位。

#### 原因剖析
- 使用 Lipgloss 渲染颜色后，字符串中会被注入不可见的 ANSI 转义序列，例如：
  `\x1b[32mclean\x1b[0m`
- 这串控制码底层占用了 14 个字节，但终端上实际只显示 `clean`（5 列宽）。
- 若使用传统格式化函数（如 `fmt.Sprintf("%-12s", statusBadge)`），因为 `14 > 12`，系统误以为已超出宽度而不追加任何空格；但终端中只能看到 5 列字符，导致该列缺少了 7 列的留白，后续列直接“贴”了上来。
- 此外，不同状态的 ANSI 序列长度不同，导致整张表格各行犬牙交错。

#### 规范与最佳实践
- **使用 ANSI 感知的宽度函数**：`lipgloss.Width()` 与 `padCell()` 会自动剥离并忽略 ANSI 控制序列，只对实际可见字符计算宽度并补齐空格。
- **选中行（Selection Highlight）颜色搭配规范**：
  - 当整行被 `selectedRowStyle`（如紫底白字）包裹时，子单元格若包含样式 Reset（`\x1b[0m`），会导致背景色被截断。
  - 因此在 `formatStatusBadge` / `formatSourceType` 中，必须接收 `isSelected bool` 参数：
    - 未选中态：展示鲜明主题色（如绿色的 `● clean`、黄色的 `▲ modified`）；
    - 选中态：使用适配高亮背景的明快前景色（如浅青/浅黄），背景透明以融入整行高亮背景。

---

### 2.3 踩坑点 3：硬编码固定列宽导致挤爆或空间浪费

#### 问题表现
- 技能 ID 较长（如超过 20 字符）或上游状态为 `update available`（16 字符）时，硬编码的列宽被强行撑开，整行后续所有列被推挤换行或错开。
- 在大尺寸终端（120~160 列）下，右侧大面积留白浪费，长路径或错误信息却被截断看不了。

#### 规范与最佳实践
- **响应式弹性列宽（Responsive Column Sizing）**：
  根据 Bubble Tea 的窗口宽度 `m.width`（通过 `tea.WindowSizeMsg` 动态更新）进行比例分配（见 `computeSkillColWidths`、`computeTargetColWidths` 等）：
  - 固定列：Indicator（2列）、来源类型（10列）、本地状态（13列）、上游状态（14列）；
  - 弹性列：技能名称（占剩余空间的约 5/8，设 Min/Max 边界保护）、详情/Hash/URL（占剩余空间的 3/8）。
- **安全截断保护（Safe Truncation with Ellipsis）**：
  当文本长度超过分配的最大列宽时，必须使用 `truncate.StringWithTail(s, uint(width), "…")` 优雅截断，并在尾部展示省略号 `…`，绝不允许超长文本撑破表格布局。

---

### 2.4 踩坑点 4：选中行背景参差不齐

#### 问题表现
使用光标上下移动选中行时，选中的深色高亮背景在每一行的末尾长短不一（因详情列文本长短不同）。

#### 规范与最佳实践
- **整行通栏平整高亮（Full-Width Row Highlight）**：
  计算整张表格各列及间隔的总宽度 `totalWidth`。在选中某行时，显式指定样式宽度：
  ```go
  if isSelected {
      row = selectedRowStyle.Width(totalWidth).Render(row)
  }
  ```
  保证高亮条横跨整张表格宽度，视觉质感与现代 CLI（如 lazygit / fzf）保持一致。

---

### 2.5 视觉呈现统一规范（Modern CLI TUI Visuals）

- **表头（Table Header）**：使用 Subtle 柔和前景色（`#B2BEC3`）加粗，表头下方使用自适应等宽分隔线（`tableSeparatorStyle`）。
- **状态胶囊（Status Badges）**：
  - `● clean`（绿色圆点，正常同步）
  - `▲ modified`（黄色三角，提示本地存在未覆盖/未提交更改）
  - `✖ missing` / `✖ invalid`（红色叉号，文件丢失或结构损坏）
  - `○ unmanaged`（浅蓝圆圈，未受管实体）
- **来源标签（Source Badges）**：
  - `git`（青色 `#00CEC9`）
  - `local`（粉紫色 `#E056FD`）
  - `managed`（橙色 `#FF9F43`）

## 3. 多语言与国际化 (i18n) 规范

> 完整规范以 [`doc/i18n规范.md`](./i18n规范.md) 为**单一事实来源**；本节仅保留历史踩坑摘要。

### 3.1 文案键名与组织规范
- 国际化文件统一放置于 `internal/i18n/`：
  - `zh_cn.go`：简体中文
  - `en.go`：英文
- 键名采用层级命名法：`<category>.<action/view>.<item>`：
  - 表头：`table.header.name`, `table.header.source`
  - 提示：`notice.updated_skill`, `notice.removed_skill`
  - 模态框：`modal.add.title`, `modal.new.placeholder`
  - 空状态：`empty.skills`, `empty.targets`

### 3.2 国际化文案踩坑点与测试规范
- **文案长度差异容错**：中文通常比英文更短，但字符宽度更大（2 列宽）。界面布局（如弹窗、帮助手册、按钮）必须预留足够的 padding 和弹性空间，避免换行撕裂。
- **测试环境隔离**：
  - 在编写单元测试时，如果直接用 `strings.Contains(view, "1. Skills")` 进行断言，当用户或 CI 环境全局语言被设置为 `zh-CN` 时，断言会因为输出的是 `"1. 技能管理"` 而失败。
  - **规范**：测试夹具中若测试特定语言视图，必须显式在测试开头初始化语言环境或使用不受语言切换影响的标识进行校验。

## 4. 文件系统与存储安全规范

### 4.1 确定性内容 Hash 校验
- 目录内容哈希统一使用 `golang.org/x/mod/sumdb/dirhash.HashDir(dir, "", dirhash.DefaultHash)`。
- 生成的哈希形如 `h1:47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=`。
- **规范**：计算哈希前必须忽略 `.git`、临时备份目录等非 Skill 内容；只要本地文件的哈希与 `catalog.json` 中记录的 `currentHash` 不一致，系统必须立即判定为 `StatusModified`，在执行更新、移除或部署时触发保护。

### 4.2 安全原子替换流程（Staged Replace Pattern）

为防止更新或添加 Skill 过程中由于断电、网络中断或磁盘写满导致工作区损坏，目录替换必须遵循严格的五阶段流程：

```text
1. 暂存 (Stage)：在目标目录的兄弟路径建立 .tmp-xxx 目录并写入新内容
       ↓
2. 备份 (Backup)：若原目录存在，将其重命名为 .bak-xxx 备份目录
       ↓
3. 替换 (Promote)：将 .tmp-xxx 原子重命名 (os.Rename) 为正式目录
       ↓
4. 更新元数据：更新 catalog.json / deployments.json 并原子落盘
       ↓
5. 清理 (Cleanup)：删除 .bak-xxx 备份目录
```

- **回滚机制**：若第 3 或第 4 步发生任何错误，必须立刻回滚恢复 `.bak-xxx`，确保工作区处于一致状态。
- **体检诊断联动**：`asoul doctor` 会自动扫描工作区遗留的 `.tmp-*` 或 `.bak-*` 暂存残留，并支持一键清理。

### 4.3 并发保护与文件锁
- CLI 和 TUI 可能并发执行。在对 `<workspace>` 或本地缓存执行写操作时，必须通过 `github.com/gofrs/flock` 锁定 `<workspace>/.asoul.lock`。
- 获取锁失败时应输出明确的友好提示，禁止发生并发脏写。

## 5. Git 缓存与网络操作规范

### 5.1 裸库镜像缓存策略
- 外部 Git 仓库克隆时，统一在本地缓存目录（`~/.cache/asoul/git/`）建立 Bare 仓库（`git clone --mirror`）。
- **聚合 Fetch 机制**：若用户添加了同一 Git 仓库下的多个 Skill，在更新检查（`asoul check`）时，系统必须以仓库 URL 为粒度去重聚合，避免对同一远端仓库重复发起多次并发 `git fetch`。

### 5.2 异步任务与 Bubble Tea 通信
- 在 TUI 中执行网络请求（如检查更新、克隆 Git 仓库）或耗时磁盘操作时，**绝对禁止在 `Update()` 主循环中同步执行阻塞调用**。
- 必须封装为 `tea.Cmd` 放入后台 goroutine 执行，并通过强类型的自定义消息（如 `discoveredSkillsMsg`、`reloadStatusMsg`、`gitProgressMsg`）回调通知主模型。

## 6. 测试与代码质量规范

1. **测试用例先行**：新增 TUI 交互或排版辅助函数时，必须在 `internal/tui/*_test.go` 中提供覆盖测试。
2. **多语言断言覆盖**：必须包含中文模式（`TestTUIChineseLanguage`）和英文模式的完整端到端测试。
3. **零外部网络依赖**：单元测试和端到端测试禁止访问真实外网 Git 仓库，必须使用本地临时目录、本地测试 bare 仓库或 Mock 消息进行全链路模拟。
4. **编译与回归要求**：提交前必须确保 `go test -v ./...` 全部通过，且 `go build -o asoul ./cmd/asoul` 编译无告警。

## 7. 已落实的安全与交互约束

以下规则是当前实现的维护边界，新增功能必须保持一致；仓库根目录的 `AGENTS.md` 提供同一份可执行检查清单。

### 7.1 路径、权限与覆盖

- 所有来自 CLI、TUI 或配置的 Skill ID 都必须先通过 `skill.ValidateID`；拼接目标路径后仍要限制在目标根目录内，不能依赖 `filepath.Join` 自行保证安全。
- 删除和覆盖前必须区分已登记、未登记和内容已变化三种状态。未登记目录、哈希读取失败或哈希不一致时，默认拒绝破坏性操作；`--force` 只用于用户明确选择的覆盖，不得绕过路径校验。
- 配置文件、备份文件和暂存目录不得扩大原有权限。包含凭据的配置默认保持私有权限。

### 7.2 部署与状态事务

- 目录部署和卸载统一采用“暂存 → 备份 → 替换/移入备份 → 写状态 → 提交清理”的顺序。状态写入失败必须恢复旧目录；备份清理失败要返回可诊断错误。
- 全局目标目录、项目格式目录和部署状态文件都要使用共享文件锁。禁止裸写 `Load → 修改 → Save`，避免并发操作互相覆盖。
- 项目卸载的 `auto` 依据已记录格式展开；未知格式必须报错，并且成功数量只能统计真实完成的格式。

### 7.3 TUI 与 CLI 行为

- TUI 的网络、Git、全量扫描和写操作放在 `tea.Cmd` 中；每个可取消操作使用独立 context，Esc 后不得处理迟到的成功结果。
- 页面渲染、光标移动和快捷键动作必须从同一个可见列表取选中项。Updates 页面不能用 Skills 页面缓存的索引代替当前行。
- CLI 的批量命令即使没有成功项也要输出合法 JSON；任一项失败都返回非零错误，并在结构化输出中保留失败 ID 与原因。

### 7.4 性能与兼容性

- 同一 Git 仓库的一次批量检查只允许刷新一次缓存，单项检查只能读取已刷新缓存。
- TUI 表格使用终端显示宽度计算和安全截断；窄终端优先压缩 Tab、底栏和次要列，不得用固定 80 列假设撑开布局。
- 相对本地源路径按调用进程的当前目录解析，并将解析后的路径用于后续更新。
